# fanmeet v1 구현 계획

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans로 태스크 단위 실행.
> **이 계획의 특수 규칙(사용자 합의)**: 코드는 Claude가 작성하되, 태스크당 작은 조각으로
> 나눠 설명과 함께 진행한다. 각 태스크 완료 시 사용자가 이해했는지 확인 후 다음으로
> 넘어간다. 코드 전문을 계획서에 싣지 않는 것은 이 합의에 따른 의도적 결정이다.
> 계획서는 목표·파일·인터페이스·테스트 케이스·완료 기준을 고정하는 계약서 역할을 한다.

**Goal:** 스트리머 팬미팅/시참 슬롯 예약 서비스 v1 — 소셜 로그인(OAuth2), JWT 인증,
SMS 휴대폰 인증·알림, PortOne 예약금 결제·환불까지 동작하는 웹 서비스.

**Architecture:** Spring Boot 모놀리스 + React(Vite) 프론트. 외부 연동(PortOne, CoolSMS)은
`PaymentGateway`/`SmsSender` 인터페이스 뒤에 격리. 정원 검증은 비관적 락 + COUNT.

**Tech Stack:** Java 21, Spring Boot 4.1(3.x OSS 종료로 착수 시 변경), Spring Security(OAuth2 Client), JPA+MySQL 8,
jjwt, PortOne 서버 SDK, CoolSMS(Nurigo), springdoc, React+Vite, Docker Compose.

**설계 문서:** `docs/superpowers/specs/2026-07-27-fanmeet-reservation-design.md`

## Global Constraints

- 금액은 정수(원화). Reservation.amount는 예약 시점 스냅샷.
- TimeSlot에 예약 카운터 컬럼 금지 — 락 + COUNT로 검증.
- Payment는 Reservation에 N:1 (결제 시도 로그). 성공 결제는 예약당 최대 1건(서비스 로직).
- 프론트가 보낸 결제 금액은 절대 신뢰하지 않는다 — 서버가 PortOne 조회로 대조.
- SMS 실패는 핵심 트랜잭션을 막지 않는다.
- 외부 API 호출부는 반드시 인터페이스(`PaymentGateway`, `SmsSender`) 뒤에.
- 시크릿(클라이언트 키, JWT 시크릿 등)은 환경변수/.env — 커밋 금지.
- Reservation.status: `PENDING_PAYMENT → CONFIRMED → CANCELLED`, `PENDING_PAYMENT → EXPIRED`.
- 브랜치: main에 직접 커밋(1인 학습 프로젝트), 태스크당 1개 이상 커밋.

**구현 중 내린 결정**

- **refresh 토큰은 JWT가 아니다.** 32바이트 무작위 + Base64. 어차피 매번 DB를 조회하므로
  자기서술적일 이유가 없고, 유출돼도 userId 같은 정보가 새지 않는다. 기존
  `JwtProvider.createRefreshToken`은 내용이 `userId+발급시각+만료시각`뿐이라 같은
  밀리초에 두 번 발급하면 **동일한 토큰**이 나와 unique 제약에 걸리는 문제도 있었다.
- **저장은 SHA-256 해시.** BCrypt는 소금 때문에 해시로 조회가 불가능하고, 토큰이 이미
  32바이트 무작위라 느린 해시가 필요 없다.
- **유저당 여러 행.** PC·폰 동시 로그인을 위해 `user_id`에 unique를 걸지 않는다.
  rotation은 사용한 행 하나만 지우고, 로그아웃도 그 기기의 토큰만 지운다.
- **쿠키 생성을 `RefreshTokenCookie`로 분리.** 로그인·재발급·로그아웃 세 곳에서 같은
  쿠키를 다루므로 속성이 어긋나지 않게 한 곳에 모았다.
- **`/api/auth/**` 와일드카드 대신 경로를 명시.** 와일드카드는 나중에 그 아래 추가되는
  엔드포인트까지 공개해 버린다. `HttpMethod.POST`까지 지정했다.
- **프론트 single-flight.** rotation 때문에 동시에 refresh를 여러 번 보내면 뒤엣것이
  이미 폐기된 토큰으로 401을 받아 멀쩡한 사용자가 로그아웃된다. 진행 중인 Promise를
  공유해 HTTP 요청이 한 번만 나가게 했다. React StrictMode가 이 상황을 개발 중에
  자동으로 재현해 준다.
- **`OAuth2SuccessHandler` 수정 필수.** 기존 코드는 refresh 토큰을 발급만 하고 DB에
  저장하지 않아, 테스트는 통과하는데 실제 로그인만 깨지는 상태였다.

**미룬 것**

- 만료된 refresh 토큰 정리 스케줄러. rotation이 정상 사용분을 지우므로 남는 것은
  이탈한 세션뿐이라 급하지 않다. v2에서 Redis로 옮기면 TTL로 자동 해결된다.
- `app.front-url`을 `AppProperties` record로 묶기. 현재 `SecurityConfig`는 필드 주입,
  `OAuth2SuccessHandler`는 생성자 주입으로 방식이 갈려 있다.
- CORS `Access-Control-Max-Age` 미설정 — 브라우저 기본값(크롬 5초)이라 프리플라이트가
  잦다. 동작에는 문제 없어 넣지 않았다.

**Steps:**

- [x] 네이버 registration/provider 추가, 파싱 분기 (+단위 테스트 1케이스)
- [x] 수동 확인 후 Commit

**구현 중 알게 된 것**

- **`openid` scope를 반드시 빼야 한다.** `CommonOAuth2Provider.GOOGLE`의 기본 scope는
  `openid, profile, email` 인데, `openid`가 있으면 스프링이 OIDC 로그인으로 판단해
  `OidcUserService`를 쓴다. 우리가 등록한 건 `.userService(...)`(일반 OAuth2용)라
  `CustomOAuth2UserService`가 **호출되지 않고**, DB 저장이 통째로 건너뛰어진 채
  SuccessHandler에서 NPE가 난다. 에러 메시지가 원인을 전혀 가리키지 않아 찾기 어렵다.
  `scope: profile, email`로 명시해 일반 OAuth2 경로를 타게 했다.
  (ID 토큰을 안 받게 되지만 사용자 정보는 userinfo 엔드포인트에서 가져오므로 무관)
- **서비스·엔티티 변경 0줄.** Task 2에서 `(provider, provider_id)` 복합 유니크와
  `findByProviderAndProviderId`를 둔 덕에 제공자 추가가 설정+파싱 분기만으로 끝났다.
  두 제공자의 식별자가 우연히 같아도 별개 계정으로 남는다.
- **`sub`를 키로 쓰고 `email`은 안 쓴다.** 이메일은 변경될 수 있어(워크스페이스 주소 변경 등)
  키로 쓰면 그 순간 다른 사람이 되어 기록이 끊긴다. `sub`는 불변이고 앱마다 값이 달라
  유출돼도 타 서비스와 대조해 동일인을 추적할 수 없다.
- `OAuthAttributes.from`을 if 나열에서 `switch`로 바꾸고 제공자별 파싱을 메서드로 분리했다.
  `@SuppressWarnings("unchecked")`가 중첩 구조를 가진 카카오 쪽에만 걸리게 된다.
- 프론트는 제공자 목록(`PROVIDERS`) 순회로 바꿨다. 제공자가 늘어도 배열에 한 줄만 추가된다.
  백엔드 주소는 `api.ts`의 `API_BASE` 하나로 모았다.

**네이버에서 추가로 알게 된 것**

- **응답이 한 겹 더 감싸여 있다.** `{ resultcode, message, response: { id, nickname } }`.
  그래서 `user-name-attribute`가 `id`가 아니라 `response`다 — 스프링은 최상위 키만 볼 수 있고
  최상위에 `id`가 없기 때문. 우리는 principal을 `userId` 기준으로 새로 만들므로 뒤쪽 영향은 없다.
- **`authorization-grant-type`을 반드시 적어야 한다.** 구글은 `CommonOAuth2Provider`가 채워주지만
  카카오·네이버는 완전 커스텀 제공자라 기본값이 없다. 빠지면 부팅 시
  `authorizationGrantType cannot be null`로 실패한다.
- **scope를 쓰지 않는다.** 네이버는 제공받을 항목을 개발자 콘솔의 "제공 정보 선택"에서 정한다.
  인가 요청의 scope 파라미터는 무시된다.

**증상이 원인에서 네 단계 떨어져 있다**

네이버 로그인이 401로 끝났는데, 실제 원인은 콘솔에서 "별명"을 체크하지 않은 것이었다.

```
별명 미체크 → response에 nickname 없음 → User.nickname NOT NULL 위반
  → 저장 실패 → OAuth2 로그인 실패 → /login?error → HttpStatusEntryPoint → 401
```

OAuth2 로그인 실패는 `/login?error`로 리다이렉트되는데, 우리는 `anyRequest().authenticated()` +
`HttpStatusEntryPoint(401)`이라 그 경로가 401로 답한다. **브라우저에서는 어떤 실패든 401로만 보인다.**
원인은 반드시 서버 로그에서 확인할 것.

**제공자 추가 시 확인 순서**

세 제공자 모두 에러 메시지가 원인을 가리키지 않았다. 코드보다 **콘솔 설정을 먼저** 볼 것.

| 제공자 | 코드 쪽 함정 | 콘솔 쪽 함정 |
|---|---|---|
| 카카오 | `client_secret_post` 필요 | — |
| 구글 | `openid` scope 제외 | 동의 화면에 테스트 사용자 등록 |
| 네이버 | `authorization-grant-type` 필요 | **제공 정보 선택에 별명 체크** |

  코드를 완료로 두면 나중에 실패했을 때 어디부터 의심할지 알 수 없어진다. Task 8은
  `SmsSender` 인터페이스만 있으면 되므로 진행에 지장이 없다.
- **`@Profile("local")` / `@Profile("sms")`로 나눴다.** Console 쪽을 `@Profile("!sms")`로 두면
  어떤 환경에서든 뜨지만, 배포에서 `sms`를 깜빡하면 아무도 모르게 문자가 안 나간다.
  지금 방식은 둘 다 아닌 프로파일에서 주입할 빈이 없어 **부팅이 실패한다.**
  배포 시 `--spring.profiles.active=prod,sms`처럼 함께 켤 것.
- **`SmsSendException`은 502.** 외부 업체 장애를 500으로 두면 우리 버그와 구분되지 않고,
  클라이언트가 재시도 가능한 실패인지 판단할 수 없다.
- ConsoleSmsSender에는 테스트를 쓰지 않았다. 로그만 찍으므로 검증할 동작이 없다.
  이 인터페이스의 존재 이유는 Task 8에서 `mock(SmsSender.class)`로 인증 로직을 테스트하는 것이다.

**구현 중 내린 결정**

- **인증번호는 평문 저장.** refresh 토큰은 해시했지만 여기서는 실익이 없다. 6자리는 100만 가지라
  해시해도 전부 미리 계산해두면 뚫린다. 방어는 수명 5분과 시도 5회 제한이 담당한다.
  해시하면 디버깅만 어려워진다.
- **번호당 한 행, 재발송은 덮어쓰기.** `phone`에 유니크를 걸고 `reissue()`로 갈아끼운다.
  만료된 행도 이 경로로 정리되므로 **정리 스케줄러가 필요 없다.** 행 수의 상한이
  "인증을 시도한 고유 번호 수"로 잡힌다. (유저×기기로 계속 쌓이는 `RefreshToken`과 다르다)
- **인증 성공 시 행을 삭제한다.** 같은 코드로 두 번 통과시키지 않기 위해서다.
  쿨다운도 함께 사라지지만, 성공했다는 건 번호의 주인이라는 뜻이라 문제되지 않는다.
  공격 경로(코드를 모른 채 발송만 반복)에서는 행이 남아 쿨다운이 걸린다.
- **`@Transactional(noRollbackFor = InvalidVerificationCodeException.class)`.** 틀렸을 때
  `recordFailure()`로 시도 횟수를 올리고 예외를 던지는데, 기본 설정이면 그 예외가 롤백을 일으켜
  증가분이 사라진다. 그러면 **시도 제한이 영원히 걸리지 않아 6자리를 무제한 대입할 수 있다.**
  단위 테스트는 mock이라 트랜잭션이 없어서 이 애노테이션을 지워도 4개 다 통과한다.
- **`verify()` 검사 순서는 잠금 → 만료 → 대조.** 만료를 대조보다 뒤에 두면 이미 만료된 코드에
  오타를 낼 때마다 남은 횟수가 깎여서, 재발송받고 온 사용자가 이미 잠겨 있게 된다.
- **엔티티가 `Instant.now()`를 부르지 않는다.** 시각을 밖에서 받아야 "5분 전에 발급된 코드"를
  테스트에서 만들 수 있다. 안 그러면 만료 테스트에 `Thread.sleep`이 들어간다.
  정책(5분·60초·5회)은 서비스가 쥐고 엔티티는 주어진 값으로 판정만 한다.
- **`ApiExceptionHandler`를 도입했다.** `@ResponseStatus`만으로는 상태 코드밖에 못 준다.
  스프링이 예외 메시지를 본문에서 지우기 때문에 만료·오답·초과가 전부 400 하나로 뭉개진다.
  **등록한 예외만** 메시지를 통과시킨다 — 기본값이 "메시지 없음"이어야 새 예외를 만들 때마다
  "이 문구를 사용자가 봐도 되는가"를 거치게 된다. 두 예외에서는 `@ResponseStatus`를 뺐다
  (상태 코드가 두 군데 적히면 언젠가 어긋난다). `InvalidRefreshTokenException`처럼
  사용자에게 보여줄 문구가 없는 예외는 그대로 `@ResponseStatus`만 쓴다.
- **`/api/phone/request`도 인증을 요구한다.** 열어두면 누구나 남의 번호로 문자를 쏘게 만들 수 있고
  비용이 우리 부담이다. 쿨다운은 로그인한 사용자의 악용을 막는 그다음 방어선이다.
- 프론트의 60초 카운트다운은 **안내일 뿐**이다. 값이 서버와 어긋나도 안내가 부정확해질 뿐
  뚫리지는 않는다. 새로고침하면 카운트다운은 사라지고, 그때는 서버의 429 메시지가 뜬다.

**미룬 것**

- **`noRollbackFor` 통합 테스트.** 단위 테스트가 못 잡는 유일한 규칙이고, 뚫렸을 때 대가가
  가장 크다(무제한 대입). `@SpringBootTest`로 "틀린 시도가 DB에 남는지" 한 케이스가 필요하다.
- **`User.phone` 유니크 제약.** 지금은 한 번호로 여러 계정을 인증할 수 있다.
  실서비스에서는 보통 막지만 계획에 없어 건드리지 않았다.
- 남은 쿨다운 초를 429 응답에 실어주기. 새로고침 후에도 정확한 카운트다운을 보여줄 수 있다.
- 정책 값(5분·60초·5회)을 `application.yml`로 빼기. 지금은 서비스의 상수다.
